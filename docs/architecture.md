# 多人在线花火：第一阶段总体设计

状态：已确认
范围：第一版实现标准 5 色规则、2–5 人实时联机、注册登录、个人对局统计、中文网页和单机服务器部署。

## 1. 产品边界

第一版提供用户名/密码注册登录、创建/加入房间、房主开始游戏、完整对局、断线重连、行动记录、文字聊天、结算、历史对局和个人统计。游戏是合作制，所有玩家共享同一分数；自己的牌只显示牌背和已知线索，其他玩家的牌正面可见。

暂不包含邮箱验证、找回密码、好友系统、匹配/ELO、观战、机器人、语音、多色/黑色火药等扩展规则。架构会为这些能力预留扩展点，但不让它们拖慢首版。

## 2. 规则基线

- 2–5 人；2–3 人每人 5 张牌，4–5 人每人 4 张。
- 标准牌组为红、黄、绿、蓝、白五色；每色 `1×3、2×2、3×2、4×2、5×1`，共 50 张。
- 初始 8 个提示标记、3 次可容错失误。每回合必须执行：给提示、打出一张牌、弃掉一张牌三者之一。
- 提示必须消耗一个提示标记，并完整指出目标玩家手中所有符合某一颜色或数字的牌；不能提示自己，也不能给“零张命中”的提示。
- 合法打牌需在对应颜色烟花堆上从 1 到 5 递增；误打会弃牌并增加一次失误。成功打出 5 时恢复一个提示标记，上限为 8。
- 弃牌恢复一个提示标记，上限为 8；提示已满时不能弃牌。
- 第三次失误立即以 0 分失败；五色全部完成时以 25 分胜利；最后一张牌被抽走后，每位玩家（包含抽到最后一张牌者）各获得最后一回合，然后按烟花堆顶之和结算。

所有规则校验只在服务端执行。客户端只表达意图，不能提交洗牌结果、下一位玩家、牌面或分数。

## 3. 推荐技术方案

采用 TypeScript 单仓库，前后端共享协议与规则类型：

```text
apps/
  web/                 React + Vite 前端
  server/              Fastify + Socket.IO 后端
packages/
  game-engine/         纯函数规则引擎、状态机、视图脱敏
  protocol/            HTTP/Socket 事件、schema 与共享类型
  ui/                  通用视觉组件与设计令牌
infra/
  nginx/               TLS、静态资源、反向代理
  docker-compose.yml   web/server/持久化数据卷
tests/
  e2e/                 Playwright 多浏览器对局
```

- 前端：React、TypeScript、Vite、React Router、Zustand、TanStack Query、Socket.IO Client、CSS Modules。
- 后端：Node.js LTS、Fastify、Socket.IO、Zod、bcryptjs、原子写入的 JSON 持久化存储。
- 测试：Vitest（规则/组件/服务）、fast-check（规则属性测试）、Playwright（多玩家端到端）。
- 工程：pnpm workspace、ESLint、Prettier、Docker Compose、GitHub Actions。

首版不引入 Redis 或独立数据库。单个 Node 进程配合原子替换的 JSON 数据文件足以支持朋友间多桌游戏，并降低部署复杂度。未来数据量或并发增长时，可将存储接口迁移到 PostgreSQL，再加入 Socket.IO Redis adapter、分布式房间锁和共享 session store。

## 4. 系统结构与信任边界

```text
浏览器 A/B/C
  ├─ HTTPS: 房间列表、创建/加入、健康检查
  └─ WSS: 房间状态、游戏指令、聊天、重连
          │
       Nginx
          │
  Fastify + Socket.IO
          ├─ Session/Room Service
          ├─ Authoritative Game Engine
          ├─ Per-player View Projector
          └─ JSON Store（Docker 持久卷）
              ├─ rooms / room_players
              ├─ games / game_players
              ├─ game_actions
              └─ game_snapshots
```

每个房间的动作在服务端串行处理：验证 `gameId + playerId + expectedVersion + actionId`，执行纯函数 reducer，事务写入动作和新版本，再分别生成每位玩家的脱敏视图并广播。`actionId` 保证重试幂等，`expectedVersion` 防止双击或延迟请求覆盖新状态。

牌堆、其他隐藏信息和随机种子永不发给客户端。对局结束前，当前玩家自己的牌对象不含 `color/rank`，只含牌位、获得的颜色/数字线索和抽牌顺序；旁观其他手牌时才含真实牌面。

## 5. 状态机

```text
LOBBY ──房主开始──> PLAYING ──牌堆耗尽──> FINAL_ROUND
  │                    │                       │
  └─离开/解散          ├─第三次失误───────────┤
                       ├─五色完成─────────────┤
                       └──────────────────────> FINISHED
```

房间内只有房主可开始；人数必须为 2–5。对局开始后玩家席位固定，短暂掉线只标记离线，不跳过回合。玩家使用浏览器保存的恢复令牌在同一席位重连；令牌只保存其哈希。首版不设置自动托管，避免服务端替玩家作出策略决定。

## 6. 核心数据模型

- `Room`：短房间码、状态、房主、设置、创建/过期时间。
- `User`：用户名、密码哈希、创建时间、累计对局/得分/游戏时长和当前房间。
- `PlayerSession`：登录令牌、用户身份和最近在线时间；重新登录后可恢复未完成房间。
- `Game`：规则版本、状态、当前座次、提示/失误数、牌堆剩余、最终回合计数、分数、状态版本。
- `CardInstance`：内部牌 ID、颜色、数字、当前区域和顺序；只存在服务端状态。
- `Knowledge`：某玩家某张牌已被明确告知的颜色、数字及线索事件。
- `GameAction`：动作 ID、玩家、类型、参数、动作前后版本、时间戳。
- `Snapshot`：定期持久化的完整服务端状态，用于宕机恢复；动作日志用于审计和回放。

聊天与游戏动作分开存储和限流。昵称、聊天长度、房间创建频率都有服务端限制。

## 7. 实时协议

HTTP 仅处理冷启动与运维：

- `POST /api/auth/register`、`POST /api/auth/login`
- `GET /api/me`（个人统计、历史对局和待恢复房间）
- `POST /api/rooms`
- `POST /api/rooms/:code/join`
- `GET /api/health/live` 与 `/api/health/ready`

Socket 客户端指令：`room:start`、`game:clue`、`game:play`、`game:discard`、`chat:send`、`state:resync`。

服务端事件：`room:view`、`game:view`、`game:event`、`chat:message`、`command:accepted`、`command:rejected`。连接或版本不一致时下发完整的“该玩家专属视图”，平时下发新视图与轻量动画事件。协议均使用 Zod schema 运行时校验。

## 8. 界面设计

参考照片的空间关系和氛围，但不复制 Board Game Arena 的商标、插画或卡面资源：

- 浅木纹桌面作为主舞台，深紫/靛蓝为牌面与信息面板主色，五种烟花色作为功能色。
- 中央是五列烟花堆、牌库数量、提示标记和失误标记；玩家手牌围绕中央分布。
- 自己的手牌靠下，以牌背展示，并用小型颜色/数字标记呈现已知信息；其他玩家显示正面牌。
- 右侧桌面端固定为操作记录与聊天，移动端收进抽屉；顶部显示当前行动提示和连接状态。
- 点击一张自己的牌后打开“打出/弃置”确认；点击其他玩家后进入提示模式，颜色/数字按钮只显示合法选项，并高亮所有命中牌。
- 当前玩家使用清晰的边框、座次箭头和状态文案三重提示，不能只靠颜色；所有关键状态兼顾色盲可辨识和键盘操作。
- 结算页显示团队分数、评价、各烟花完成度，并提供“再来一局”和“返回大厅”。

响应式目标：桌面 `>= 1024px` 保持照片中的环桌布局；平板压缩侧栏；手机改为纵向玩家带 + 中央棋盘 + 底部操作栏。最低支持近两年的 Chrome、Safari、Firefox、Edge。

## 9. 测试与验收

规则引擎重点覆盖：牌组数量与洗牌确定性、发牌张数、提示全命中、提示/弃牌边界、合法与误打、成功打 5 回提示、三次失误、空牌堆最终轮、满分立即结束、每位玩家视图绝不泄露自己的牌。

并发测试覆盖：重复动作幂等、非当前玩家出牌、旧版本动作、同一席位多连接、掉线重连、服务重启后恢复。端到端测试启动 2–5 个独立浏览器上下文，完成建房、加入、整局、刷新重连和结算。

完成标准：

1. 规则测试和协议测试全绿，核心规则分支覆盖率不低于 95%。
2. Playwright 能稳定跑通 2 人和 5 人对局，并验证不同玩家看到的牌面不同。
3. 重连后房间、手牌知识和轮次一致；重复点击不会产生双动作。
4. Docker Compose 在一台全新 Linux 服务器上一条命令启动，具备 HTTPS、数据库迁移、健康检查和持久化卷。
5. 360px 手机到 1440px 桌面无关键控件遮挡，基础键盘操作和对比度检查通过。

## 10. 部署与运维

生产环境使用单台 Linux 服务器：Nginx 终止 TLS，托管前端静态文件并代理 `/api` 与 `/socket.io`；应用由 Docker Compose 管理。JSON 数据文件放在命名卷中并采用临时文件原子替换，部署时应对该卷提供每日加密备份、日志轮转和恢复说明。

环境变量只放服务端：数据库连接、session 签名密钥、允许的 Origin、日志级别。容器以非 root 用户运行；设置安全响应头、请求体上限、房间/聊天限流和 WebSocket Origin 校验。日志使用结构化 JSON，并带 `requestId/roomId/gameId`，但不记录恢复令牌或完整隐藏牌堆。

## 11. 第二阶段实施顺序

1. 初始化单仓库、共享协议、CI 与 Docker 开发环境。
2. 完成纯函数规则引擎和高覆盖单元/属性测试。
3. 完成游客 session、房间生命周期、Socket 协议和持久化。
4. 完成大厅、牌桌、提示/出牌/弃牌交互及响应式布局。
5. 完成断线重连、幂等并发、聊天、日志和结算。
6. 完成多浏览器 E2E、安全与可访问性检查、生产部署文档。
7. 在本机以 Docker Compose 做最终验收，交付服务器部署命令和运维手册。

## 12. 请确认的设计决策

进入第二阶段前，默认按以下决策实施：

- 仅标准 5 色规则；扩展规则后续加入。
- 首版使用用户名/密码注册登录，密码只保存安全哈希。
- 对局中途掉线会等待重连，不自动代打或跳过。
- 单服务器、单应用实例，不为早期规模预先引入 Redis/Kubernetes。
- UI 接近参考图的布局与氛围，但全部使用原创的卡面、图标和纹理。
